#sr-due 
overlayFS - это специальная файловая система в Linux, которая позволяет накладывать несколько слоёв директорий друг на друга (overlay)
### Идея
- Ты говоришь ядру:
	Сделай мне view такой, что верхний слой накладывается на нижний
- При чтении:
	Если файл есть в верхнем upperdir, он берётся оттуда
	Если нет - из нижнего
- При записи:
	Всё идёт всегда в верхний слой
	Если файл есть в lowerdir, он копируется в upperdir, и уже там модифицируется

Почему отдельная ФС, а не просто использовать общую папку как базу и отдельные для изменений?
Ответ: 

|🚧 **Проблема без overlayFS**|✅ **Как overlayFS решает**|
|---|---|
|**Нужны специальные программы**|overlayFS на уровне ядра даёт единый каталог (`merged`), любая программа (`nginx`, `bash`, `ls`) работает без изменений.|
|**Нет автоматического поиска в двух местах**|overlayFS прозрачно ищет: сначала в `upperdir`, потом в `lowerdir`. Программы думают, что это одна FS.|
|**Удаление — огромная проблема** (удалишь файл в «своей папке», а он снова появится из «общей базы»)|overlayFS делает whiteouts (`.wh.*`), скрывающие файлы из `lowerdir` для твоего overlay.|
|**Нужно вручную копировать файлы для изменений (copy-up)**|overlayFS автоматически делает copy-up: при изменении файла из `lowerdir` он копируется в `upperdir`.|
|**Невозможно безопасно делить базу между контейнерами**|overlayFS позволяет 100 контейнерам использовать одни и те же `lowerdir`, но каждый контейнер имеет свой `upperdir` для изменений.|
|**Невозможно сделать атомарные операции (rename, unlink)**|overlayFS через `workdir` поддерживает atomic операции для overlay.|
|**Нет прозрачной экономии места (copy-on-write)**|overlayFS хранит общий read-only base (`lowerdir`), а пишет только изменения — экономит гигабайты.|
