#sr-due 
- Readiness != Liveness: делай разные эндпоинты
	- Readiness может зависеть от внешних ресурсов 
	- Liveness должен быть самым простым и локальным, иначе будешь убивать сервис при временных DB-глюках
- Startup включай для тяжёлых стартов - это лечит "ложные" рестарты liveness
- HTTP vs TCP vs Exec vs gRPC
	- HTTP → самый информативный (коды 200–399 = успех).
	- TCP → минимальный (порт открыт = успех), годится для простых сервисов.
	- Exec → дорогой, может быть шумным; используй, если других опций нет.
	- gRPC → ок, если реализован стандартный health-check сервис.
- Не ставь маленький `timeoutSeconds` и слишком частый `periodSeconds` на нагруженных нодах — будет шум и ложные падения.
- Для сетей/mesh (sidecar) иногда полезен readiness на **127.0.0.1** и нужном контейнерном порту; не забудь `readinessGate` если используешь внешние контроллеры (редкий кейс).

### Быстрые «рецепты» тюнинга
- **Максимальное время на старт** с `startupProbe`:  
    `T ≈ initialDelay + failureThreshold * period` → посчитай и задай с запасом.
- **Readiness под нагрузкой**: увеличь `timeoutSeconds` до 3–5, `failureThreshold` до 3–5, чтобы редкие пики не выбивали из Endpoints.
- **Liveness**: не ставь слишком агрессивно; цель — «вылечить клин», а не «реагировать на любую просадку».
